Specialization needs a system contract.

Specialized compute and heterogeneous integration advanced faster than the disclosed contracts for programming, data placement, isolation and qualification. The useful architectural question was how the complete machine would behave under a real workload.

Patterns in the reviewed Q&A

Programmability leaves isolation work.

P4 described trusted program control but deferred concurrent independent-program virtualization. Vega's guest ownership mechanism did not supply switching-latency figures. A programming interface alone did not establish predictable tenant sharing. T1 128:59 ↗

Locality shapes useful throughput.

Volta's tensor reduction depended on the kernel/framework and intermediate placement. Cisco's serial-attached memory traded capacity and connectivity against higher latency and I/O power. Peak arithmetic and link bandwidth hid different costs. S1 95:08 ↗

Packaging needs economic and test evidence.

EMIB questions probed access, cost and known-good-die assurance. EPYC's organic package prompted performance and die-yield questions. Integration feasibility did not settle supplier access, usable yield or the complete platform tradeoff. S5 62:41 ↗

Formats and software constrain specialization.

Brainwave questions pressed precision and accuracy assumptions. TPU exchanges examined workload size, sparsity and framework selection. AWS F1 required manual partitioning across FPGAs. Hardware specialization still demanded model and application work. S5 117:55 ↗

Timing figures need complete paths.

Arm defined L2 timing from address generation through the access path; system atomic details remained incomplete. EPYC's encryption answer discussed latency against coherence behavior. A cycle count or coherent address did not specify the whole transaction. S8 57:57 ↗
